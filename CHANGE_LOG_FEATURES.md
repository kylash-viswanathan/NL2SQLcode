## 2026-09-15 — Agent behavior & data-design fixes (found during first real run)

- **Planner over-declining**: the Planner agent was refusing PII questions itself (e.g. "What is a client's SSN?"), short-circuiting before the SQL was ever generated. Access control for sensitive data is the HITL gate's job, not the Planner's — updated the prompt in `agents/planner.py` to only decline truly out-of-domain questions.
- **Sensitivity tagging too aggressive**: `full_name`, `email`, `phone`, `address` were tagged `PII` in `config/sensitivity_tags.yaml`, so governance masking (Layer 4) blanked them out in *every* result — including basic "which clients have X" lookups, making the assistant useless for its core job. Retagged those four columns `confidential` (still HITL-gated, but visible once a reviewer approves) and kept `ssn`, `account_number`, `date_of_birth` as `PII` (always masked regardless of HITL outcome). Re-ran `ingestion.schema_crawler` + `knowledge.build_index` to refresh the embedded schema descriptions.
- **Response agent quality**: the Response agent was summarizing ("2 clients matched") instead of directly answering with the requested identifying details (client names). Tightened `agents/response.py`'s system prompt to require listing identifying items from the result rows, not just counts/summaries.
- **Golden set data mismatch**: `evaluation/golden_set.yaml`'s `reference_sql` for "What are the holdings in the Alice Growth Portfolio?" only selected `ticker, quantity`, while the agent (correctly, matching the curated exemplar for that exact question) also returns `cost_basis` — the DeepEval judge flagged the extra field as "unsupported." Aligned the reference SQL to include `cost_basis`.

### Verification performed

- Smoke test: normal question ("How many clients do we have?") answered correctly end-to-end through all 4 layers.
- Smoke test: sensitive question ("What is Alice Nakamura's SSN and account number?") correctly triggered the HITL interrupt, and governance masking blanked `ssn`/`account_number` in the response regardless of approval.
- `pytest evaluation/deepeval_tests.py -v` → **12/12 passed** (11 golden-set correctness checks + 1 HITL/masking check).

## 2026-09-15 — Chainlit UI: schema display, sample-query dropdown, live progress

- **Schema visibility**: `app.py`'s `on_chat_start` now renders the sample DB schema (table/column/type/sensitivity) as a markdown table, read from `ingestion/schema_metadata.json`, so users see what's queryable without leaving the chat.
- **Sample-query dropdown**: added a `cl.ChatSettings` `Select` widget ("Try a sample question", gear icon) populated from `evaluation/golden_set.yaml`'s questions — reusing the existing curated golden set rather than duplicating a second list. Selecting a question echoes it as a user-style chat bubble and runs it through the same pipeline as a typed message (`on_settings_update` → `_process_query`).
- **Live per-stage progress**: while a query runs, a `cl.TaskList` (Planner → Schema-Linking → SQL Generation → HITL Gate → Execution → Governance → Response) plus a text progress bar (`🟩⬜ NN%`) update in real time as each LangGraph node completes. Required switching the UI from `graph.invoke()` (blocking, single result) to `graph.stream(..., stream_mode="updates")` (yields one chunk per completed node) — added `agents/runner.py::stream_start_question`, `stream_resume_with_decision`, and `get_current_state` (reads the full final state back from the checkpointer once the stream is exhausted, since `stream_mode="updates"` chunks are partial per-node, not the accumulated state). The blocking `graph.stream()` generator runs in a background thread and is bridged to the async Chainlit UI via a `queue.Queue` + `asyncio.to_thread(queue.get)` loop, so the event loop stays responsive between node completions.
- Verified chunk/interrupt shapes directly against the compiled graph before wiring into the UI: normal runs yield `{node_name: partial_state}` once per node in execution order; HITL-triggering runs yield a final `{"__interrupt__": (Interrupt(value={...}),)}` chunk instead of continuing — matches the existing `result["__interrupt__"][0].value` handling already used for the non-streaming path.
- Chainlit headless boot confirmed no registration/import errors from the new handlers (`on_settings_update`, `TaskList`/`Task`/`ChatSettings`/`Select` usage) — `HTTP 200` on `localhost:8000`.

## 2026-09-15 — Starter cards weren't rendering

User feedback: no Starter cards appeared on the welcome screen; the sample questions only showed up at the bottom of the side panel (moved there in the previous fix as a fallback reference list).

- **Root cause**: Chainlit only displays `@cl.set_starters` cards on a truly empty, message-free welcome screen. `on_chat_start` was sending a `cl.Message` (with the schema reference attached as a `display="side"` element) immediately — that message being present flips the client out of the "empty" state and suppresses the Starters, even though the server-side `set_starters` wiring itself was registered correctly (confirmed by reading `chainlit/server.py`: starters are fetched unconditionally into the `/project/settings` payload — the suppression is a frontend welcome-screen state check, not a config/registration issue).
- **Fix**: `on_chat_start` no longer sends any `cl.Message`. The schema/sample-question reference now goes through `cl.ElementSidebar.set_title()` + `set_elements()` instead — this opens the side panel via a session-level event independent of the message thread, so it no longer interferes with the empty-welcome-screen state Starters depend on. The app's intro text moved from a runtime message into `chainlit.md` (Chainlit's dedicated welcome-screen doc, rendered above Starters without adding a thread message).
- Verified: compiles clean; Chainlit headless boot still `HTTP 200` with no registration errors. (The `ElementSidebar.set_title`/`set_elements` calls themselves only execute in a real client session — not exercised by the headless boot check, which only confirms the app registers without import/syntax errors; needs the user's interactive click-through to fully confirm the sidebar auto-opens and Starters now render.)

## 2026-09-17 — Langfuse tracing wired in, following Langfuse's own best practices

Installed the official [Langfuse AI Skill](https://github.com/langfuse/skills) (`.claude/skills/langfuse/`, fetched from the source repo and saved as a project-scoped skill) and followed its 4-step instrumentation workflow (assess → verify baseline → run and self-audit real traces → invite the user to explore) rather than instrumenting from memory. `observability/langfuse_setup.py` already had the `langfuse.langchain.CallbackHandler` framework integration from earlier scaffolding, but it had never actually been exercised end-to-end with real credentials — this session turned it on and hardened it:

- **PII masking on export** (`mask_otel_spans`, the current-recommended Python SDK masking hook — the legacy `mask` param was rejected after checking the fetched-fresh docs): regex-redacts SSN/account-number/email/phone patterns from every span attribute before export. This matters beyond the app's own governance masking (`governance/masking.py`, which only masks columns tagged `PII` in the final response) because the raw `execution_rows` state — including real SSNs/account numbers for a HITL-approved sensitive query — briefly exists un-redacted between the Execution and Governance nodes, and would otherwise be shipped verbatim to Langfuse Cloud, a third-party SaaS.
- **Descriptive, low-cardinality trace names**: `answer-nl2sql-question` / `resume-hitl-review`, replacing no explicit name (previously whatever LangChain auto-derived). Verb-first, no dynamic values embedded — per the best-practices page's explicit "keep dynamic values out of names" rule.
- **Session grouping for HITL pause/resume**: switched from ad hoc `config["metadata"]["langfuse_session_id"]` to the SDK's `propagate_attributes(session_id=thread_id, trace_name=...)` context manager (the metadata-dict approach doesn't support setting `trace_name`, only `user_id`/`session_id`/`tags`). A HITL-interrupted question now produces two traces (question + resume) grouped into one session — matches Langfuse's own guidance for "workflow spans multiple requests with human-in-the-loop steps in between."
- **Noise removed** (`should_export_span`): self-auditing a real trace against the best-practices page ("is there noise you don't need?") surfaced that LangGraph's internal `route_after_*` conditional-edge functions were showing up as their own trace-tree nodes — pure control-flow glue, not application steps. Filtered them out at the client level.
- **Eval-run tagging + required flush**: `evaluation/deepeval_tests.py` now tags golden-set runs with `propagate_attributes(tags=["golden-set-eval"])` (distinguishes them from live Chainlit traffic in Langfuse) and flushes at pytest session teardown via a session-scoped autouse fixture — the skill's docs call out "no flush() in scripts" as the most common instrumentation mistake for short-lived processes. Chainlit also flushes on `@cl.on_chat_end`.
- **Self-audit performed on real traces** (required step, not skipped): ran the instrumented path end-to-end for both a normal question and the seeded PII question, fetched the resulting observations via the Langfuse REST API, and confirmed — model name + token usage present on every `GENERATION` observation, `answer-nl2sql-question`/`resume-hitl-review` trace names showing correctly, both traces of a HITL pair sharing one `sessionId`, and — the critical check — the `execution` node's exported `output` showing `"execution_rows": [["***MASKED-SSN***", "***MASKED-ACCOUNT***"]]` instead of the real values. Re-ran after each fix until clean.

## 2026-09-17 — Critic / Evaluation Agent

Planned before building (per the user's request): worked through what the Critic agent should do and how it's complementary to, not redundant with, the HITL gate — HITL is access control (is a human allowed to let this query touch this data? — on column sensitivity, decided by a human, pre-execution); the Critic is quality control (is this actually a correct answer? — on faithfulness, decided by an LLM judge, post-execution, since it needs the real result set to judge against). A query can be sensitive-and-correct, sensitive-and-wrong (HITL alone can't catch this — the Critic is the only thing that does), or non-sensitive-and-wrong (the Critic is the only safety net at all). Confirmed with the user on two open design calls before implementing: (1) exhausted-retries behavior → return the answer with a "could not be fully verified" caveat rather than escalating to a second human-review mechanism (would blur the HITL/Critic split); (2) retry budget → share `retry_count`/`max_self_heal_retries` with Execution's existing self-heal counter rather than tracking a separate one, for v1 simplicity.

- **`agents/critic.py`** (new): single LLM-as-judge call (`gpt-4.1-mini`) given `{question, sql, masked_columns, masked_rows}`, returns PASS or `FAIL: <reason>`. Explicitly instructed that masked values (`***MASKED-...***`) are expected governance behavior, not a defect to flag — otherwise every HITL-approved sensitive query would trivially fail the critic. Auto-passes without an LLM call when `execution_error` is already set (a HITL rejection or an already-exhausted execution retry) — nothing for it to judge in that case.
- **`agents/graph.py`**: inserted `critic` between `governance` and `response`. On fail, routes back to `sql_generation` (same loop topology the execution self-heal retry already uses, so the regenerated query flows back through the HITL gate naturally); on fail with retries exhausted, still routes to `response`.
- **`agents/state.py`**: added `critic_passed: Optional[bool]`, `critic_reason: Optional[str]`.
- **`agents/response.py`**: prepends a "⚠️ This answer could not be fully verified (...)" caveat when `critic_passed is False` (i.e. it failed and retries ran out).
- **`agents/sql_generation.py`**: generalized the retry-context prompt wording from "the previous attempt failed with this database error" to "the previous attempt failed" — critic-triggered retries reuse the same `last_error` context-feeding mechanism, and the old wording would have been misleading (falsely implying a DB error) for a critic-triggered retry.
- **`app.py` / `agents/runner.py`**: added `critic` to `STAGE_ORDER` and the Chainlit progress-bar labels (`STAGE_PHASE_WORD["critic"] = "Verifying"`) — without this the UI progress bar would have silently topped out at 6/7 stages.
- Deliberately **not** wired to the golden set (`evaluation/golden_set.yaml`) in v1 — see the updated `Project Documents/Agent_Orchestration_Flow.md`, which now marks the Critic as implemented but the offline DeepEval→SME-curation→golden-set-update loop as still just the proposed design, not built.

### Verification performed

- Streamed a normal question end-to-end: critic fires, `critic_passed: True`, no caveat.
- Streamed the seeded PII question through interrupt + approve: critic correctly does **not** flag the masked result as a defect (`critic_passed: True`) — confirms the "masking is expected, not a failure" instruction works.
- Streamed the PII question through interrupt + **reject**: critic auto-passes without an LLM call (execution_error already set), rejection message passes through unmodified — confirms the short-circuit path.
- Full `pytest evaluation/deepeval_tests.py -v` re-run with the critic in the loop: **12/12 still pass** — no regression from the added node.
- Chainlit headless boot after adding `critic` to `STAGE_ORDER`: `HTTP 200`, no errors.

**Follow-up decision**: asked what testing/scoring framework the Critic uses — answer is none, it's a hand-written LLM-as-judge prompt, independent of DeepEval's `GEval` correctness metric used offline. Flagged that DeepEval's metric classes can be invoked directly (`GEval(...).measure(test_case)`) outside `pytest`, so the live Critic could in principle reuse the exact same rubric/threshold as the offline golden-set scoring instead of two judges that can drift apart. User's call: leave the Critic as a standalone LLM-as-judge for MVP, document unifying it with DeepEval's `GEval` as a Phase 1+ idea rather than build it now (noted in `CLAUDE.md`'s Critic section).

## 2026-09-17 — MVP scope audit + DeepEval → Langfuse score attachment

User asked for an audit of planned-but-not-built MVP features. Cross-checked `CLAUDE.md`'s stated Phase 0 success criteria and the architecture doc's Layer 4 description against actual code (also grepped for stray `TODO`/`FIXME`/stub markers — none found). Found one real gap: **"DeepEval scores are visible in Langfuse for every run"** (a stated success criterion, and explicitly called out in the architecture doc: *"DeepEval's scores are pushed into Langfuse and attached to the originating trace"*) was not actually true — `observability/langfuse_setup.py::score_trace()` existed but was never called anywhere in the codebase. DeepEval runs were traced into Langfuse (as agent-execution traces, tagged `golden-set-eval`), but the correctness score itself never made it there.

Fixed in `evaluation/deepeval_tests.py`:
- **`_run_scored()`** (new): the trace a `graph.invoke()` call produces normally closes (and its ID becomes unrecoverable) before the calling function returns, which is a problem when you want to score that exact trace *after* computing the DeepEval result. Fixed by pre-generating a trace ID via `Langfuse.create_trace_id()` and explicitly running the graph inside `client.start_as_current_observation(as_type="evaluator", name=..., trace_context={"trace_id": trace_id})` — this forces that specific ID onto the whole nested LangGraph run, so it's still known (and correct) after the `with` block exits.
- **`test_golden_question`**: switched from `assert_test(test_case, [correctness_metric])` (which only returns pass/fail, no score access) to calling `correctness_metric.measure(test_case)` directly, reading `.score`/`.reason` off the metric object, pushing them to the trace via `score_trace()`, then asserting `correctness_metric.is_successful()` manually — same pytest pass/fail behavior as before, plus score access.
- **`test_sensitive_query_triggers_hitl_and_masking`**: also pushes a `deepeval-hitl-masking` boolean score (1.0/0.0) to its trace — this test doesn't use `GEval`, but the same "scores visible in Langfuse for every run" criterion applies to it too.

### Verification performed

- Ran 3 tests (2 golden-question, 1 sensitive) and fetched the results back via Langfuse's `GET /api/public/v3/scores` (with `fields=details,subject`) — confirmed `deepeval-correctness` (0.93, 0.995) and `deepeval-hitl-masking` (1.0) scores landed, each with `subject.id` pointing to a distinct trace ID and the GEval reason text in `comment`.
- Fetched observations for one of those trace IDs via `GET /api/public/v2/observations` — confirmed the `deepeval-golden-question` evaluator span correctly nests the *entire* LangGraph run (Planner → ... → Critic → Response, including all `GENERATION` calls), not an empty wrapper.
- Full `pytest evaluation/deepeval_tests.py -v`: **12/12 still pass** after the rewrite.
